# Git, PR, 보안

## Git 및 PR

- 작업 전 `git status --short --branch`로 현재 브랜치와 변경사항을 확인한다.
- `dev`를 기본 통합 브랜치로 사용한다. 기능 브랜치는 `dev`에서 만들고, PR도 `dev`로 올린다.
- `main`은 안정 릴리스 브랜치로 사용한다. 릴리스 가능한 상태일 때만 `dev`를 `main`으로 병합한다.
- 하나의 PR은 하나의 논리적 변경에 집중한다.
- `main`과 `dev`에는 직접 push하지 않고 PR로만 병합한다.
- 작업 브랜치는 Jira 티켓 키를 포함해 `<type>/<JIRA_PROJECT_KEY>-<issue_number>-<description>` 형식으로 작성한다.
- 허용 브랜치 타입은 `feature`, `fix`, `chore`, `docs`, `refactor`, `test`다.
- 브랜치 설명은 소문자 kebab-case를 사용한다.
- 커밋 메시지는 한글 Conventional Commits 형식으로 작성한다.
- 예: `feat(auth): 로그인 화면 구현`, `fix(layout): 모바일 헤더 깨짐 수정`, `docs: 에이전트 지침 정리`
- 커밋 전 관련 검증 명령을 실행하고 결과를 PR 설명에 적는다.
- PR 제목, 본문, 리뷰 응답은 한글로 작성한다.
- PR 제목은 `[<JIRA_PROJECT_KEY>-<issue_number>] <한글 제목>` 형식으로 작성한다.
- PR에는 변경 요약, 주요 판단 이유, 테스트 결과, 관련 이슈 또는 Jira 티켓 키, UI 변경 시 스크린샷 또는 확인 URL을 포함한다.
- Codex 리뷰는 스타일 취향보다 실제 버그, 접근성, 반응형 레이아웃, 상태관리 오류, API 계약, 누락된 테스트를 우선한다.
- 사용자가 만들었을 수 있는 변경사항을 임의로 되돌리지 않는다.

## Codex 리뷰 요청

PR을 올린 뒤 PR 코멘트에 `@codex review`로 시작하는 리뷰 요청을 남긴다. 리뷰 요청, 리뷰 코멘트, 리뷰 응답은 한글로 작성한다.

```text
@codex review

프론트엔드 관점에서 다음을 중점적으로 봐줘:

- 실제 런타임 버그가 있는지
- 접근성 문제가 있는지
- 모바일/데스크톱 반응형 레이아웃이 깨지는 부분이 있는지
- React Server Component와 Client Component 경계가 적절한지
- 상태관리나 서버 상태 캐싱이 잘못된 부분이 있는지
- API 요청/응답 계약과 에러/로딩 상태 처리가 빠진 곳이 없는지
- 테스트에서 빠진 실패 케이스나 회귀 위험이 있는지

스타일 취향보다 실제 버그, 운영 리스크, 유지보수 리스크를 우선해서 봐줘.
```

## 보안 및 설정

- `.env`, 토큰, API key, 개인 인증 정보는 커밋하지 않는다.
- 공개 저장소에 민감한 로그, 응답 payload, 사용자 데이터를 남기지 않는다.
- 새 환경변수가 필요하면 `.env.example`에 이름과 용도를 문서화한다.
- 의존성 추가는 실제 필요가 있을 때만 한다.
